# 슬라이스 구현 운영 규율

status: active
기준일: 2026-08-08
적용 범위: 이 저장소에서 **플랜 → 구현 위임 → 검수** 루프로 진행하는 모든 작업

AGENTS.md가 역할 분담과 검증 신뢰 원칙을 정한다면, 이 문서는 **한 슬라이스를 실제로 굴릴 때
무엇을 적고 무엇을 확인하는가**를 정한다. 아래 규칙은 전부 실제로 결함을 잡은 것만 남겼다 —
잡은 사례를 함께 적어 두었으니, 의례로 보이면 그 사례를 먼저 읽는다.

전투 육각 리워크에서 축적됐지만 **전투에 한정되지 않는다.**

---

## 1. 플랜에 정지 조건을 적는다

구현자가 **우회하지 말고 멈추고 보고할** 조건을 플랜에 명시한다. 적지 않으면 구현자는
막힌 자리를 스스로 메우고, 그 메움이 설계 결정이 되어 조용히 굳는다.

표준 목록:

1. 기존 테스트가 하나라도 값이 바뀌면
2. fingerprint가 바뀌면
3. **플랜 서술이 실제 코드와 다르면** — 코드가 이긴다. 단 그 사실을 반드시 보고한다
4. 플랜이 두 가지로 읽히면
5. 동결된 파일에 부족한 것이 있으면
6. 시작 시점 baseline 수치가 예상과 다르면

> **잡은 사례.** 버전 강제 슬라이스에서 검증을 배선하자 65개 테스트가 떨어졌다.
> 구현자가 우회하지 않고 멈춘 덕에 **트리에 두 simulation version이 공존하고 있었다는 사실**이
> 드러났다. 우회했다면 검사를 약화시켜 통과시켰을 것이고 결함은 그대로 남았을 것이다.

## 2. 기대값을 조용히 고치지 못하게 한다

**가장 값이 큰 규칙이다.** 다만 판정과 표시를 구분해야 규칙이 살아 있다.

### 판정에 영향을 주는 변경 — 절대 수정 금지

> 기대값을 새 결과에 맞춰 고쳐야 통과하는 상황이 오면 **멈추고 보고한다.**
> 그건 플랜의 분석이 틀렸다는 뜻이고, 슬라이스를 오늘 착지시키는 것보다 그 사실을 아는 게 중요하다.

### 표시·투영이 바뀌는 변경 — 이유를 댈 수 있을 때만

투영식이나 포맷이 바뀌면 기대값이 **바뀌는 게 정상**이다. 그때는 규칙을 이렇게 바꿔 적는다.

> 움직인 이유를 새 계산식으로 설명할 수 있을 때만 고친다.
> 설명할 수 없는 값 변화가 있으면 멈추고 보고한다. 바뀐 기대값 전부를 이유와 함께 목록으로 보고한다.

**둘을 뭉개면 규칙이 무의미해진다.** 전자에 후자의 여유를 주면 회귀가 통과하고,
후자에 전자의 엄격함을 적용하면 구현자가 정당한 변경을 못 하고 멈춘다.

## 3. 보고서를 믿지 않는다

AGENTS.md의 검증 신뢰 원칙 그대로다. 영향이 큰 검증은 오케스트레이터가 **직접 재실행**한다.

슬라이스마다 최소한 이것들:

```bash
cargo fmt --all -- --check
cargo test --workspace --no-fail-fast    # 수치가 감소하면 회귀다
git diff --check
cd web && npm test                        # web을 건드렸다면
```

그리고 명령으로 안 잡히는 것:

- `git diff --name-only <base>..HEAD` — **소유 범위 밖 변경**이 있는가
- 금지 파일이 정말 무변경인가
- 여러 줄 바뀐 테스트 diff를 **열어서** 기대값 수정인지 픽스처 변경인지 구분

> **잡은 사례.** 한 구현자가 "4개 파일"이라 보고한 픽스처 문제가 직접 세어 보니
> **7개 파일 9곳**이었다. 보고가 악의적이어서가 아니라 자기가 밟은 범위만 봤기 때문이다.

## 4. 두 갈래로 검증한다

"기존 값이 안 바뀌었다"만 확인하면 **아무것도 강제하지 않은 변경이 초록으로 통과한다.**
무언가를 고치는 슬라이스에는 두 가지를 함께 요구한다.

1. 고정 테스트 값이 그대로인가 (**회귀가 없는가**)
2. **의도한 것이 실제로 달라졌는가** (**효과가 있는가**)

> **잡은 사례.** 점유 강제 슬라이스에서 ②를 별도로 요구했더니, 좌표 궤적이 실제로
> "관통하며 좌우가 뒤바뀜"에서 "인접해서 정지, 아군이 항상 왼쪽"으로 바뀐 것이 확인됐다.
> ①만 봤다면 점유 코드가 실제로 작동하는지 알 수 없었다.

관련 기법: 구현자에게 **가드를 임시로 제거해 해당 테스트가 실제로 실패하는지** 확인시킨다.
"테스트가 있다"와 "테스트가 그걸 잡는다"는 다르다.

## 5. 실측한 뒤에 넘긴다

플랜을 쓰기 전에 오케스트레이터가 직접 숫자를 재고, **그 예측을 플랜에 명시**한다.

> 예: "두 전투원이 모두 `r = 0`에 있어 육각 거리가 `|dq|`로 줄어들고 기존 유클리드 거리와
> 정확히 같으므로, 좌표 교체가 이 전투의 거동을 바꾸지 않아야 한다."

예측을 적어 두면 두 가지가 생긴다. 맞으면 구현자가 확인만 하면 되고,
틀리면 **구현자가 즉시 알아챈다.** 구현자에게 발견하게 맡기지 않는다.

임계값을 다룰 때는 특히 그렇다. 예: 픽스처를 옮겨야 할 때 "**정확히 한 칸만** 옮겨라"까지 지정한다 —
필요 이상으로 벌리면 의도치 않은 임계값을 넘을 기회가 늘어난다.

## 6. 슬라이스 분할

운영 정본([Combat_System_Operating_Guide.md](Combat_System_Operating_Guide.md) §5)의 규칙에 더해:

- **다음 단계의 schema를 미리 확정하지 않는다.** 앞 슬라이스가 확정한 public contract와
  테스트를 보고 다음 플랜을 쓴다. 그래서 앞 슬라이스의 보고서에 **확정된 public API 전체 서명**을
  요구한다 — 그게 없으면 다음 플랜을 쓸 수 없다.
- **쪼갤 수 없는 슬라이스가 있다.** 타입 교체처럼 여러 크레이트가 동시에 컴파일돼야 하는 변경은
  중간 상태가 없다. 그런 경우 **위험한 부분을 앞 슬라이스로 미리 빼낸다** —
  예: 좌표 교체 전에 좌표 수학만 순수 모듈로 만들어 테스트로 못박았다.
- 위험한 것과 비싼 것을 분리한다. **가장 틀리기 쉬운 것**(수학·규칙)과
  **가장 되돌리기 비싼 것**(직렬화 경계·save schema)은 다른 슬라이스여야 한다.

## 7. 이 저장소에서 밟기 쉬운 함정

### 7-1. 소유 파일 목록 — 컴파일 때문에 바뀌는 파일

**세 슬라이스 연속으로 틀렸다.** 원인은 매번 같다: "의미적으로 바뀔 파일"만 세고
**"컴파일되려면 바뀌어야 하는 파일"**을 빠뜨린다.

구조체에 필드를 추가하면 그 구조체를 명시적 리터럴로 만드는 **모든** 파일이 깨진다.
`Default`가 없으면 스타일 문제가 아니라 하드 컴파일 에러다.

**대책**: 필드 추가·타입 변경 슬라이스에는 코드를 건드리기 전에 생성 지점을 세는 WP를 **맨 앞**에 둔다.

```bash
grep -rln "<StructName> {" crates/
```

이걸 넣은 슬라이스에서는 **착수 5분 만에** 목록이 나왔고 중간에 멈추는 일이 없었다.

### 7-2. cargo·npm은 클라우드 컨테이너에 있다

AGENTS.md는 "cargo·wasm-pack·gh는 WSL에만 있다"고 적는데 그건 **사용자 머신** 기준이다.
클라우드 컨테이너에는 cargo와 npm이 있다. 구현자에게 명시하지 않으면
"환경 탓에 검증 불가"라는 보고가 나온다 — AGENTS.md에 정확히 그 환각 보고 사례가 기록돼 있다.

**없는 것: `wasm-pack`.** 그래서 `npm run qa:storybook:visual`은 앱이 상호작용 상태에
도달하지 못해 5뷰포트가 전부 실패한다. **회귀 때문이 아니다.**
구현자에게 "돌릴 수 없으면 못 돌렸다고 적어라, **통과했다고 적지 마라**"를 명시한다.

`web/node_modules`가 비어 있으면 `npm ci`가 선행돼야 한다.

### 7-3. 생성물은 재생성한다

`crates/escape-core/fixtures/content/**`와 `web/src/data/generated/**`의 번들은 export 산출물이다.
**손편집하지 말고** `scripts/export_web_data.py`로 재생성한다.

주의: 생성 번들 하나가 `web/` 아래 있어서 "web 무변경" 같은 소유 규칙 문구와 충돌하기 쉽다.
경로를 명시해서 쓴다.

또한 런타임 Rust 생성 텍스트는 **wasm 바이너리**에 들어가므로 export 스크립트가 아니라
wasm 재빌드가 필요하다 (AGENTS.md).

### 7-4. simulation version bump가 필요한 때와 아닐 때

- **필요**: 직렬화 표현이 바뀔 때 (`{x,y}` → `{q,r}`)
- **불필요**: `#[serde(default, skip_serializing_if = ...)]`로 **미설정 시 키가 아예 안 나타날** 때

bump가 필요해 보이면 먼저 **"기본값이 현재 동작이고 키가 사라지게 할 수 있나"**를 확인한다.
이 방식으로 두 슬라이스가 bump 없이 필드를 추가했다.

역직렬화는 막지 않는다 — 옛 version이 박힌 저장 기록은 계속 읽혀야 한다.
금지되는 것은 그 version으로 **새로 시뮬레이션을 돌리는 것**이다.

### 7-5. 패닉 정책

이 크레이트들은 어디서도 패닉하지 않는다. 잘못된 입력은 `Result`로 거부하고 산술은 checked다.

`.expect()`는 **구조적으로 도달 불가능한 경우에만** 허용한다.
"실제로 일어날 수 있는 실패를 삼키는" 코드와 반드시 구분한다.

> **잡은 사례.** 한 구현자가 점유 실패를 `let _ =`로 버렸다. 그러면 이미 점유된 타일을 요청한
> 참가자가 점유 맵에서 빠져 **그 타일이 빈 칸으로 읽히고 이동 차단이 조용히 작동하지 않는다.**
> 이동을 시험하지 않는 스위트에서는 영원히 안 보인다. 전용 오류 전파로 교체했다.

### 7-6. 주석이 자기 코드를 부정하는 경우

모듈 주석이 불변식을 선언해 놓고 코드가 그걸 어기는 일이 실제로 있었다.
나중에 들어온 구현이 주석을 갱신하지 않아서다. **모두가 읽는 대신 믿기 때문에 살아남는다.**

발견하면 주석을 **실제 동작대로** 고치고, 그 모순이 결정을 필요로 하면 미결 항목으로 등록한다.
어느 쪽이 옳은지를 지나가는 슬라이스가 정하지 않는다.

## 8. 오케스트레이션 루프 — subagent로 실제로 굴리는 법

한 사람(또는 한 에이전트)이 **오케스트레이터와 구현자를 겸하지 않는다.** 역할을 나누는 이유는
인력 문제가 아니라 **검수가 성립하려면 쓴 사람과 검사하는 사람이 달라야** 하기 때문이다.
자기가 쓴 플랜대로 자기가 구현하면 플랜의 오류가 구현의 오류로 그대로 흘러간다 —
이번 세션에서 플랜 오류 세 건을 전부 **구현자가** 잡았다.

### 8-1. 한 슬라이스의 흐름

```
오케스트레이터: 실측 → 플랜 작성 → 커밋·푸시
     ↓ 위임 (격리된 worktree)
구현자:         baseline 확인 → WP 순서대로 → 커밋 → 보고서
     ↓
오케스트레이터: 직접 재검증 → (결함 시 수정 지시 후 재개) → 머지 → 다음 플랜
```

**오케스트레이터가 위임하면 안 되는 것 두 가지:**

1. **검증.** 보고서의 숫자를 그대로 옮기지 않는다. 직접 돌린다(§3).
2. **다음 플랜 작성.** 앞 슬라이스의 보고서에서 확정된 public contract를 읽고 직접 쓴다.
   구현자에게 "다음 것도 알아서 해"를 주면 슬라이스 경계가 사라진다.

### 8-2. 모델 tier

AGENTS.md의 tier 규칙을 따른다 — 오케스트레이터는 상위 모델, 구현은 중간 모델, 조회·요약은 경량.
이번 세션은 구현 전부를 중간 tier(medium effort)로 돌렸고 **충분했다.**
구현자가 오케스트레이터의 플랜 오류를 잡아낸 것도 그 tier에서 일어났다.

### 8-3. 병렬 실행

**파일이 겹치지 않는 슬라이스는 병렬로 돌린다.** 각 구현자를 **격리된 git worktree**에 넣으면
커밋이 서로 섞이지 않는다. 이번 세션은 두 슬라이스(버전 강제 / 육각 수학 모듈)를 동시에 돌렸고
전자는 `combat_contract.rs` 계열, 후자는 신규 파일 + `lib.rs` 한 줄이라 충돌이 없었다.

`lib.rs`처럼 **양쪽이 다 건드리는 파일**이 있으면 병렬로 두되 머지 순서를 정해 둔다.
겹치는 범위가 실질적이면 병렬로 하지 않는다.

### 8-4. 재개 vs 새로 띄우기

**재개가 기본이다.** 구현자는 이미 플랜과 코드를 읽어 둔 상태라 그 컨텍스트가 아깝다.

재개가 맞는 경우:

- **구현자가 정지 조건에 걸려 멈췄을 때.** 소유 범위를 넓히거나 판단을 내려서 재개시킨다.
  이번 세션에서 두 번 있었고 둘 다 재개가 옳았다.
- **검수에서 결함을 찾았을 때.** 수정 지시를 보내 같은 구현자가 고치게 한다.
- **API 한도 등으로 중단됐을 때.** 단, 먼저 worktree에 **잃은 작업이 있는지 확인**한다
  (`git log`, `git status`). 이번 사례는 탐색 단계라 잃은 게 없었다.

새로 띄우는 게 맞는 경우: 슬라이스가 다르거나, 앞 구현이 방향을 크게 잘못 잡아 컨텍스트가 오히려 방해될 때.

### 8-5. squash 머지 뒤의 히스토리 갈림 — 실제로 밟았다

PR을 **squash** 머지하면 main의 커밋이 브랜치 커밋들과 다른 SHA가 된다.
그 뒤에 브랜치를 새 main에서 재시작하면, **머지 전 tip에서 갈라져 나온 구현자 worktree**는
같은 내용인데도 머지 시 충돌한다. 실제로 3파일 충돌이 났다.

**해법: 머지하지 말고 델타만 뽑아 얹는다.**

```bash
git merge --abort
git diff <구현자가-갈라져나온-커밋>..<구현자-브랜치> > /tmp/slice.patch
git apply --check /tmp/slice.patch && git apply /tmp/slice.patch
# 적용 후 검증을 다시 돌린다
```

이러면 그 슬라이스가 실제로 바꾼 것만 정확히 얹힌다.
**적용 뒤 반드시 전체 검증을 다시 돌린다** — 패치가 깨끗하게 붙었다는 것과 결과가 맞다는 것은 다르다.

### 8-6. 머지 후 브랜치 재시작

PR이 머지되면 그 브랜치에 새 커밋을 쌓지 않는다. 최신 main에서 같은 이름으로 재시작한다.

```bash
git fetch origin main
git checkout -B <branch> origin/main
```

이후 푸시는 `--force-with-lease`가 필요하다(브랜치가 머지 전 커밋을 가리키고 있으므로).
머지된 이력만 들어 있을 때는 안전하다.

### 8-7. PR 단위

**슬라이스 여러 개를 한 PR에 쌓지 않는 편이 낫다.** 리뷰 단위가 작아야 검수가 실제로 일어난다.
다만 한 트랙을 완결하는 슬라이스들(예: 좌표계 교체 a/b/c/d)은 묶어도 읽힌다.
판단이 서지 않으면 사용자에게 묻는다 — 이번 세션에서 실제로 물어서 "지금 머지, 다음은 새 PR"로 정했다.

## 9. 위임 지시서에 반드시 넣는 것

- 읽어야 할 정확한 플랜 경로와, 그 전에 읽을 코드 파일
- 소유/수정 가능 파일과 **수정 금지 파일**
- 확인해야 할 **시작 baseline 수치**
- **정지 조건** (§1)
- 기대값 규칙 — 판정인지 표시인지 명시 (§2)
- 이 슬라이스에서 **틀리기 쉬운 지점**과 그게 왜 위험한지
- 검증 명령과 **실제 숫자 출력을 붙여넣으라는 요구**
- 보고 형식, 그리고 다음 플랜에 필요한 산출물(예: 확정된 public API 서명)
- 실패를 정직하게 보고하라는 명시 — *"낙관적인 보고보다 정확한 실패 보고가 훨씬 유용하다"*
