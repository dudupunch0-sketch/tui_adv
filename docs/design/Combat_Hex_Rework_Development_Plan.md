## 0. 이 문서의 위치

이 문서는 **개발 플랜**이다. 방향, 트랙 분해, 트랙 간 의존, 결정 항목을 소유한다.

`fable_<주제>_step1_<YYMMDDHHMM>.md`로 따로 만든다 (AGENTS.md의 플랜 문서 컨벤션).
여기서 다음 단계의 schema를 미리 확정하지 않는다 —
[Combat_System_Operating_Guide.md](../dev/Combat_System_Operating_Guide.md) §5의 분할 규칙을 따른다.

배치 위치: 이 문서는 한 slice의 구현 지시서가 아니라 전투 방향 문서이므로 repo 루트가 아니라
`docs/design/`에 둔다. 구현 단계 추적은 계속
[Combat_System_Implementation_Plan_Index.md](Combat_System_Implementation_Plan_Index.md)가 소유한다.

## 1. 레퍼런스와 그 취급

레퍼런스는 사용자가 제공한 육각 타일 오토배틀러의 스크린샷 5장과 전투 1라운드 영상 2편
(9초 + 14초, 합계 23.5초, 0.8배속 녹화)이다.

**차용 대상은 전투 1라운드의 화면과 규칙까지다.** 그림체는 차용하지 않는다.
레퍼런스는 픽셀아트지만 이 프로젝트의 시각 정체성은 수묵 먹 실루엣 + 한지 토큰이며
(AGENTS.md의 확정 결정), 가져오는 것은 **정보 문법**이다: 칸 분할 체력 바, 플로팅 피해 수치,
상태 스택 표기, 스킬명 말풍선, 점유 타일 하이라이트, 대시 경로 잔광, 타겟 연결선.

### 레퍼런스 실측 요약

영상 프레임 분석으로 확인한 사실이다. 추정과 구분해 적는다.

| 항목 | 실측 |
|---|---|
| 격자 | 육각(flat-top), 세로로 눌린 준투시. 격자선 상시 표시 |
| 점유 표시 | 점유 타일마다 테두리. **아군 흰/회색, 적 붉은 갈색**으로 색 분리 |
| 다칸 이동 | `랜스 돌격!` 시 5칸 이상 직선 관통 + 육각 잔광 트레일 + **경로상 3기 동시 피격** |
| AoE | 육각 타일 모양 링을 지면에 그림 |
| 버프 표기 | 3단 — 값 포함 라벨 칩(`방어 관통 25%`) → 스킬명 말풍선(`각인 개방!`) → 대형 반투명 월드 텍스트(`각인 개방 8중첩`) → HP 바 위 아이콘 슬롯 잔류 |
| 2단 바 | 위 = 체력(칸 분할, 진영별 색), 아래 = 스킬 게이지(회색↔주황 충전 관찰) |
| 개전 연출 | 각 유닛에서 목표로 베지어 곡선(아군→적 청록, 적→아군 적색), 수 초 후 소멸 |
| 적 카운트 | `2/2 → 2/5 → 3/8 → 0/8` — **분모가 증가**한다(전투 중 증원) |
| 카메라 | 고정 뷰 아님. 교전 지점을 따라 팬·줌 |
| 배속 | `0.8x` 확인 — 1x/2x 이분법이 아님 |
| 규모 | 아군 3 vs 적 누적 8, 보이는 격자 약 11×7 |
| 길이 | 교전 개시 → 웨이브 클리어가 1배속 환산 약 16~19초 (**웨이브 1개** 기준) |
| 개입 | 23.5초 내내 플레이어 조작 없음 — 레퍼런스는 순수 관전형 |

미해결: 유닛 주변 흰색 `F` 글리프의 정체. 깃발 마커인지 폰트 잔상인지 불명. 우선순위 낮음.

## 2. 확정된 방향

사용자 결정(2026-08-06)이다. 임의 변경 금지.

1. **파견/웨이브/보스/복귀 루프는 차용하지 않는다.** 전투 1회 = 인카운터 1개라는 현행 위상을 유지한다.
2. **개입을 유지한다.** 0~3회, 개입 플래그 발생 시 정지, 선택이 전투에 영향을 준다.
3. **육각 타일로 교체한다.**
4. **픽셀아트로 가지 않되, 나중에 교체하기 쉽게 시스템화한다.**
5. **톤은 프로젝트 것을 따른다.** 레퍼런스의 명명에 구속되지 않는다.
6. 전투는 하나의 웨이브 또는 보스전으로만 구성된다. 웨이브 사이 휴식·상점 없음.
7. **적이 먼저 배치되고, 플레이어가 이후 자기 유닛을 배치한다.**
8. 배치 구역은 기본 왼쪽 절반이되 **절대 규칙이 아니다** — 적 침범, 함정/이벤트에 의한 시작 위치 변동을 허용한다.
9. 플레이어 행동은 배치 / 전투 전 준비 / 전투 중 0~3회 개입 세 가지뿐이다.
10. 개입 종류: 스킬 발동, 버프 사용, 특정 유닛 명령, 긴급 구조, 오브젝트 조작.
11. 이동은 타일 단위, 점유 개념 존재, **이동 예약**(AI가 다음 목적지를 미리 확정) 존재.
12. 대형 유닛은 2칸 이상 점유, **회전 없음**(점유 형태 고정).
13. 다칸 이동의 결과는 밀어내기 / 이동 취소 / 인접 대체 중 하나이며, 스킬·스탯·특성·기믹이 판정에 영향을 준다.
14. 금색 게이지 = 스킬 자원(마나 유사).
15. **공격속도는 플레이어에게 숫자로 노출하지 않는다.** 내부 계산이며 UI에는 핵심 스탯만 표시한다.
16. 피해 수치 색: 피격 빨강 / 감쇠(약한·비효율·내성) 회색 / 일반 흰색 / 치명타 노랑.
17. 적 카운트는 웨이브 전체 기준 고정 분모(`8/8 → 0/8`).
18. 기본 4기 vs 8기. 상한은 코드에 고정하지 않는다.
19. 회복은 캐릭터/장비/스킬의 특성으로 존재하는 **일반 메커닉**이다.
20. 긴급 구조 = 포위된 아군의 포위망 해제를 최우선 과제로 바꾸는 **명령 변경**이다.

### 2-1. 상충 해소 결정

레퍼런스 실측과 위 결정이 갈린 지점의 처리다.

| 쟁점 | 레퍼런스 | 결정 | 해소 |
|---|---|---|---|
| 적 카운트 | 분모 증가(증원) | 고정 분모(17) | **표기는 고정 분모, 등장은 시차 진입.** 8기를 처음부터 필드에 놓지 않고 나눠 투입한다. 플레이어는 총량을 처음부터 알고, 전투 밀도는 증원 효과를 얻는다 |
| 분홍 점선 | 실측은 적 점유 테두리 | 이동 예약(11) | **두 레이어 모두 채택.** 점유 하이라이트(진영별 색)와 이동 예약 표시(파선)는 별개다 |
| 유닛 상한 | — | 상한 없음(18) | **하드코딩 제거 + 콘텐츠 소유.** `ParticipantLimit`의 4/8을 없애고 인카운터 데이터가 정한다. 무제한이 아니라 소유권 이전이며, §5의 성능 예산이 실질 상한이 된다 |
| 대형 유닛 형태 | — | 정삼각형/정사각형(12) | 육각 격자에 정사각형 대응물이 없다. **점유 형태를 axial 오프셋 집합으로 데이터화**한다(예: 정삼각형 = `[(0,0),(1,0),(0,1)]`). 회전 없음은 오프셋 고정으로 자연히 만족된다 |

비대칭 주의: 회전이 없으므로 비대칭 형태(삼각형)는 좌우가 마주 보는 배치에서 아군·적이 같은 방향을
향한다. 대칭이 필요한 유닛은 대칭 형태(2칸 도미노, 7칸 꽃)를 쓰도록 콘텐츠 가이드에 명시한다.

## 3. 유지해야 하는 하드 불변식

리워크가 깨면 안 되는 기존 계약이다. 트랙별 구현 플랜은 이 목록을 상속한다.

1. **결정론.** 같은 manifest · seed · 선택 이력 · simulation version은 같은 결과와 로그를 만든다.
2. **RNG 분리.** story resolution / encounter composition / actual combat / forecast ensemble /
   cosmetic presentation 5개 namespace를 섞지 않는다. forecast는 실제 전투 RNG를 재사용하지 않는다.
3. **renderer는 판정하지 않는다** (정본 13). 렌더러는 core가 이미 정한 값을 포맷만 한다.
   피해 범주, cue, 승패, 집계, 로그 중요도를 렌더러가 재계산·추정하지 않는다.
4. **순서 독립성.** 전투원·공격 정의의 입력 순서가 결과를 바꾸지 않는다
   (`simultaneous_mutual_defeat_is_independent_of_attack_definition_order` 등이 고정).
5. **누설 차단.** 숨은 판정(공격 굴림), 억제 사유, Hidden/Conditional 효과 id는 어느 로그에도 나가지 않는다.
   **여기에 공격속도를 추가한다** (결정 15).
6. **additive-optional 직렬화.** 기존 JSON 경계를 깨는 변경은 `simulation_version` bump를 동반한다.
7. **reduced-motion 정지 상태.** 모든 연출은 reduced-motion에서 올바른 최종 정지 프레임을 갖는다.
8. **신규 색상 리터럴 금지.** 기존 한지/먹 토큰만 쓴다.
9. **UI 금지 항목.** 전략 평가, 핵심 전환점 자동 표시, 원인 분석, 전략 조언, 종합 MVP, 이전 전투 비교를 제공하지 않는다.

## 4. 현재와 목표의 격차

`escape-core`는 이미 **결정론 + 동시 tick + 좌표 위 자동 전투 + 관전 view 분리**라는
레퍼런스와 같은 뼈대를 갖고 있다. 방향이 어긋난 게 아니라 해상도가 낮다.

부족한 것은 세 층이다.

- **공간 층** — 타일·점유·충돌이 없다. `CombatPosition{x,y}`는 무한 정수 평면이고
  `collision_radius`는 선언만 되어 이동 해석에서 읽히지 않는다. 실측 결함으로 **말들이 서로를 통과한다**.
- **시간 층** — tick은 있으나 "누가 언제 행동하는가"가 없다. 전원이 매 틱 이동하고,
  `resolve()`가 매 틱 모든 공격 정의를 무조건 발동한다. 쿨다운·행동 주기·공격속도가 전무하다.
- **표현 층** — core가 판정을 다 갖고 있는데 관전 표면으로 내보내는 어휘가 cue 5종
  (Attack/Hit/Evade/BalanceBroken/Incapacitated)뿐이다. 수치·스택·스킬명·연쇄 처치를 그릴 데이터가 없고,
  불변식 3 때문에 렌더러가 만들어낼 수도 없다.

### 이미 예약되어 있는 자리

리워크가 새로 발명하지 않아도 되는 것들이다. 선언만 되고 소비되지 않는 필드가 많다.

| 필드 | 현재 | 쓰일 곳 |
|---|---|---|
| `CombatSimulationParticipant.support_range` | 검증만 되고 **아무 데서도 읽히지 않음** | 회복·지원 사거리 (T5) |
| `CombatRoleWeights` 8개 중 5개 (`formation_maintenance`, `protect_priority`, `target_priority`, `risk_tolerance`, `ability_priority`) | 선언만, **소비 0** — 실제로 읽히는 건 `preferred_distance`·`pursuit_range`·`aggression` 3개뿐 | 긴급 구조(=`protect_priority`), 명령 변경 개입 (T4) |
| `CombatManifest.public_info_ids` | 검증만 | 배치 시점 정보 공개 범위 (T6) |
| `CombatState.environment_states` (`distance`/`pressure`/`visibility`) | 검증만, 시뮬레이션이 소비 안 함 | 오브젝트 조작 (T7) |
| `CombatRolePreset` / `CombatTargetPolicy` | 목표 선택에만 부분 사용 | 전투 전 준비, 명령 변경 개입 (T4/T6) |
| `CombatPresentationSpeed` (`OneX`/`TwoX`/`Instant`) | 실행 결과에 실려만 있고 UI 미노출 | 재생 배속 (T0에서 위치 이동) |
| `CombatEffectInstance` + `stacking_group` | core에 있으나 스택 수를 표면으로 안 내보냄 | 상태 스택 표기 (T8) |

## 5. 규모 제약 (설계 전제)

2분 전투가 만드는 데이터 규모는 아키텍처 선택을 강제하므로 설계 전제로 못박는다.

현재 저작된 전투는 `tick_millis: 100`, `max_ticks: 10` — **1초 8틱**이다. 2분이면 **1,200틱**,
150배다. 현재 구조는 매 틱 전 보드 상태를 통째로 직렬화하고, `scene_page_from_turn_view`의
combat producer는 **렌더할 때마다 전투를 처음부터 재실행**한다(캐싱 미구현).

| 항목 | 현재(8틱, 2명) | 2분(1200틱, 12명) |
|---|---|---|
| `frames[].pieces` | 16 | **14,400** |
| `full_log` | 32 | **26,000+** |
| `ScenePage.combat` JSON | 수 KB | **수 MB** |

지금은 결정론이라 재실행 결과가 같아서 문제가 드러나지 않았을 뿐이다. 2분 전투에서는 그대로 터진다.

**대응은 T4가 소유한다**: 세그먼트 단위 저장(개입 구조상 어차피 필요) + 델타 인코딩(변한 말만 기록)
+ 논리 tick 굵기 재조정. 세 번째는 "화면 시간 = 시뮬레이션 시간"(I1)을 건드리므로 T4에서 별도 결정한다.

## 6. 개발 트랙

각 트랙은 목적 / 소유 범위 / 완료 판단 기준 / 리스크를 갖는다. 트랙 하나가 구현 플랜 하나는 아니다 —
큰 트랙은 여러 slice로 쪼갠다.

### T0. 기반 정리 (전제)

**목적.** 이후 모든 breaking change를 안전하게 만든다.

**범위.**
- `simulation_version` 실제 강제 검증. 현재 저작이 선언한 값을 코드가 그대로 기록에 실어 보내며,
  코드가 구현하지 않는 version을 적어도 아무도 잡지 못한다. 정본 03의 "결정성은 같은 version
  내부에서만 보장한다"가 코드로 강제되지 않는 상태다.
- `CombatPresentationSpeed`를 `CombatExecutionResult`에서 재생 레이어로 이동.
  배속은 판정에 영향을 주지 않으므로 실행 결과에 있을 이유가 없다.

**완료 판단.** 미구현 version을 선언한 픽스처가 index-time에 거부된다. 기존 픽스처 전체가 새 version으로 이관된다.

**리스크.** 픽스처 전수 이관이 필요해 diff가 넓다. T1의 breaking change와 **같은 bump에 묶는 것이 낫다** — T1 착수 시 함께 처리할지 별도 선행할지는 T1 구현 플랜에서 결정한다.

### T1. 육각 좌표계와 점유

**목적.** 공간 층을 만든다. 리워크의 기반이며 거의 모든 트랙이 여기 의존한다.

**범위.**
- `CombatPosition{x,y}` → axial `(q, r)`. 육각 거리·인접·경로 helper.
- 점유 맵. 1타일 1유닛.
- 대형 유닛 = axial 오프셋 집합, 회전 없음.
- **파생 상태 제공**: 포위 판정(인접 6칸 중 적 점유 비율) — T4의 긴급 구조가 이걸 쓴다.
- 경계 갱신: `ScenePage.combat` → WASM JSON → `escape-terminal/src/snapshot.rs`,
  web `renderCombatStage.ts`/`combatMotion.ts`/`types.ts`, 픽스처·번들 2종.

**완료 판단.** 두 유닛이 같은 타일을 점유할 수 없다. 기존 실측 결함("말이 서로를 통과해 좌우가 뒤바뀐다")이 회귀 테스트로 봉인된다. 대형 유닛이 자기 오프셋 집합의 모든 타일을 점유한다.

**리스크.** breaking change. `simulation_version` bump 필수(T0). 직렬화 경계가 넓어 slice 분할이 필요하다.

### T2. 타일 배정 해소 (이동 예약 · 충돌 · 밀어내기)

**목적.** 동시 tick에서 타일 경합을 결정론적으로 푼다.

**범위.**
- 이동 예약 테이블. AI가 목적지를 확정하고 여러 틱에 걸쳐 이동한다.
  현재의 매 틱 즉석 `step_toward` 계산을 대체한다.
- **밀어내기 / 이동 취소 / 인접 대체를 한 해소 단계로 통합**한다. 한 틱의 모든 이동 의도를
  수집한 뒤 일괄 해소하며, 결정론적 기준(밀어내는 힘 → 동점 시 id)을 쓴다.
- 다칸 이동(대시·순간이동)과 **경로 타격**.

**왜 한 단계로 묶는가.** 밀어내기는 본질적으로 순차적이다(A가 B를 밀고 B가 C를 민다).
지금 코드는 `BTreeMap` id 정렬로 결정론만 지키고 있는데, "id 알파벳 순서가 전투 결과를 정한다"는
받아들일 수 없고 불변식 4(순서 독립성)도 깬다. 의도 수집 → 일괄 해소로 분리하면 순서 독립성이 유지되고,
결정 13이 요구한 세 결과(밀어내기·취소·대체)가 자연히 한 곳에 모인다.

**완료 판단.** 입력 순서를 섞어도 같은 결과가 나온다. 연쇄 밀어내기가 결정론적으로 해소된다.
같은 타일을 두 유닛이 동시에 목표해도 한 쪽만 들어간다.

**리스크.** 이 트랙이 리워크에서 규칙적으로 가장 어렵다. 예약 상태가 tick 간 유지되어야 하므로
참가자 상태가 늘고, 세그먼트 재개(T4) 시 예약도 복원되어야 한다.

### T3. 행동 주기

**목적.** 시간 층을 만든다.

**범위.**
- 유닛별 행동 주기. 이동 주기와 공격 주기를 분리한다.
- 현재의 "매 틱 모든 공격 정의 발동"을 제거한다.
- 공격속도는 스탯·스킬·패시브·장비에서 내부 계산되며 **노출하지 않는다**(불변식 5에 추가).
- 논리 tick 굵기 재검토(§5와 연동).

**완료 판단.** 서로 다른 주기의 유닛이 같은 전투에서 다른 빈도로 행동한다.
공격속도가 어떤 로그·관전 표면에도 나타나지 않는다.

**리스크.** 결착 조건·로그·fingerprint가 전부 바뀐다. 기존 밸런스 픽스처(`..._first_hit_damage_is_1333_hundredths` 등)가 재산정된다.

### T4. 실행 모델 · 개입 · 지속

**목적.** 개입을 결정론 안에서 성립시킨다. **리워크에서 가장 중요한 트랙이다.**

**범위.**

*(a) 세그먼트 실행.* 현재는 전투 전체를 한 번에 계산한 뒤 재생하는 배치 구조다. 개입이 결과를
바꾸려면 이렇게 바뀌어야 한다.

```
core가 tick 0..k 실행 → opportunity 감지로 "k에서 정지"를 결정론적으로 판정
  → 세그먼트[0..k] 프레임 + 개입 마커를 렌더러에 전달
  → 렌더러는 k까지 재생하고 정지
  → 플레이어 선택
  → 선택을 입력으로 세그먼트[k+1..] 실행
```

**개입 지점은 core가 정하고 렌더러는 거기까지 재생 후 멈춘다.** 그러면 "시뮬레이션 정지"와
"재생 정지"가 같은 tick에서 일치한다. 렌더러가 임의 시점에 멈추면 개입 시점이 wall-clock에
의존해 결정론이 깨지고(불변식 1), 렌더러가 정지 시점을 판단하면 불변식 3을 깬다. 둘 다 피한다.

*(b) 세그먼트별 seed 파생.* 지금은 전투 1회 = seed 1개다. 선택 이후 구간의 난수가 선택 내용에
의존하되, 같은 선택 이력이면 같은 결과가 나와야 한다. 정본 불변식이 이미 "선택 이력"을 전제하지만
코드에 경로가 없다.

*(c) 전투 진행 상태 저장.* 매 렌더 재실행 모델을 폐기한다. §5의 규모 문제와 같은 답이다.
델타 인코딩과 논리 tick 굵기도 여기서 결정한다.

*(d) 개입 되먹임 3종.*
- **즉발 효과** → 재개 직전 `state`에 1회 적용 (기존 `CombatEffectInstance` 경로 재사용)
- **명령 변경** → 재개 이후 지속되는 `roles`/`policies` 교체 (**기존 필드 그대로**)
- **둘 다** → 위 조합

*(e) 긴급 구조.* 포위 판정(T1의 파생 상태)을 개입 기회 조건으로 삼고, 선택 시
`protect_priority`를 최우선으로 올린다. AI 목표에 "누구를 구하러 갈까"를 추가한다 —
현재 `CombatTargetPolicy`는 "누구를 때릴까"만 정한다.

**완료 판단.** 같은 선택 이력이 같은 전투 기록을 만든다. 다른 선택이 다른 결과를 만든다.
2분 전투가 렌더마다 재실행되지 않는다. 배속을 바꿔도 결과가 동일하다.

**리스크.** 트랙 중 가장 넓다. save schema 결정을 포함하므로 되돌리기 비싸다. 최소 3~4 slice.

### T5. 판정 모델 확장

**목적.** 표현 층이 그릴 수 있는 판정을 core에 만든다.

**범위.**
- **치명타.** 결정 16의 노란 수치를 위한 신규 판정.
- **감쇠 플래그.** 회색 수치가 요구하는 약한 피해·비효율·내성 감소는 원인이 셋이지만 표시는 하나이므로,
  core는 플래그 하나만 내면 된다.
- **스킬 자원 게이지.** 금색 바. 현재 `CombatResolutionCombatant`에는 health/balance뿐이다.
- **회복.** 피해 정의의 대칭형. `support_range`(예약된 미사용 필드)를 사용하고,
  **최대 체력 상한 clamp를 추가**한다 — 현재 체력은 `.max(0)` 하한만 있다(피해만 있어서 불필요했다).

**주의.** 결정 16은 연출 요구가 아니라 **판정 모델 확장 요구**다. 렌더러가 숫자 크기나 비율로
피해 범주를 추측하면 불변식 3 위반이다.

**완료 판단.** `CombatAttackOutcome`이 피해 범주를 스스로 말한다. 회복이 최대 체력을 넘지 않는다.

**미결.** 전투불능(체력 0) 이후 회복으로 복귀 가능한가 — §7 참조.

### T6. 배치 단계

**목적.** 결정 7~9의 플레이어 배치를 만든다. 현재 코드에 배치 단계가 전혀 없고
`CombatSimulationParticipant.position`은 authoring이 고정한다.

**범위.**
- 배치 구역 데이터화 — 기본 왼쪽 절반, 인카운터가 예외를 정의할 수 있게(결정 8).
- 적 선배치 + 공개 범위 — `CombatManifest.public_info_ids`가 그 자리다.
- 배치 검증 — 구역 안인가, 점유가 겹치지 않는가, 대형 유닛의 오프셋 집합이 전부 들어가는가.
- 전투 전 준비(역할·우선 목표) 설정 — `CombatRolePreset`/`CombatTargetPolicy`가 이미 그 자리다.

**완료 판단.** 잘못된 배치가 index-time/입력-time에 거부된다. 같은 배치가 같은 전투를 만든다.

### T7. 오브젝트 조작

**목적.** 결정 10의 개입 중 오브젝트 조작.

**범위.** `CombatState.environment_states`(`distance`/`pressure`/`visibility`)를 시뮬레이션이
소비하게 한다. 현재 검증만 되고 읽히지 않는다.

**우선순위.** 후순위. T1(좌표)·T4(개입)이 먼저 서야 오브젝트가 놓일 자리가 생긴다.

### T8. 관전 표현 문법 확장

**목적.** cue 5종으로는 부족한 어휘를 채운다. 불변식 3 때문에 **core가 내보내야** 한다.

**범위.**
- 신규 표현 데이터: 스킬명, 상태 스택 수, 피해 범주(T5), 연쇄 처치, AoE 범위(타일 집합),
  대시 경로(타일 열), 개전 시 타겟 링크.
- 유닛 위 표시: 칸 분할 체력 바, 스킬 게이지, 상태 아이콘 슬롯.
- 플로팅 수치 4색(결정 16).
- 점유 하이라이트(진영별 색) + 이동 예약 표시(파선) 2레이어.
- **로그 도배 방지.** 정본 13의 "원시 사건을 연관 전투 상황으로 묶는다"는 아직 미구현이며,
  현재도 `move_intent`/`damage_applied` 반복이다. 1200틱이면 치명적이 된다.

**완료 판단.** 렌더러가 어떤 판정도 추측하지 않는다. 2분 전투의 core log가 읽을 수 있는 분량이다.

### T9. 표현 레이어 교체 가능성

**목적.** 결정 4 — 나중에 픽셀아트로 갈아끼울 수 있게 한다.

**범위.**
- **고정 타일 메트릭 투영.** 현재 web은 전 프레임 min/max로 정규화해 %로 투영한다.
  이 방식은 아트 에셋·격자와 정렬이 불가능하다. 타일 폭/높이/세로 압축률 기반 투영으로 바꾼다.
- **말 외형의 단일 교체 지점.** 현재 `renderCombatStage.ts`가 실루엣 마크업을 직접 뿜는다.
- **크기와 점유의 분리.** 레퍼런스 실측(메카는 스프라이트가 크지만 1타일, 보스는 2타일 이상)이
  그대로 계약이 된다. core는 점유(규칙)만 소유하고 스프라이트 크기는 렌더러 소관이다.

**완료 판단.** core 데이터 변경 없이 외형 모듈 교체만으로 시각이 바뀐다.

### T10. HUD

**목적.** 결정 17의 적 카운트와 파티 카드.

**범위.** `위험 개체 n/m`(고정 분모), 파티 카드(초상화·체력·스킬 게이지·상태 아이콘).
**`LV`와 경험치는 제외한다**(결정 1 — 메타 성장 비차용).

### T11. 콘텐츠와 밸런스

**목적.** 2분 전투를 실제로 성립시킨다.

**범위.**
- 2분 밸런스. 레퍼런스의 3v8이 16초에 끝나는 밀도로는 2분을 채울 수 없다.
  유닛 수·체력·행동 주기·**시차 진입**(§2-1)으로 시간을 만든다.
- 개입 간격. 2분에 0~3회면 30~40초당 1회다. 개입 기회 감지 임계값을 여기 맞춘다.
- 정본 11의 표준 전투원 수치 재설정 — T3가 행동 주기를 넣으면 기존 값이 무의미해진다.
- 게이트 플래그 `combat_spectator_preview_unlocked` 제거 시점 판단.

## 7. 트랙 순서와 의존

```
T0 기반 정리
 └─ T1 육각 좌표·점유  ← 리워크의 기반
     ├─ T2 타일 배정 해소
     ├─ T3 행동 주기
     │   └─ T4 실행 모델·개입·지속   ← 가장 중요, 가장 넓음
     │       └─ T7 오브젝트 조작
     ├─ T5 판정 모델 확장
     │   └─ T8 관전 표현 문법
     ├─ T6 배치 단계
     └─ T9 표현 레이어 교체 가능성

T10 HUD        (T8과 함께)
T11 콘텐츠·밸런스 (전부 선 후)
```

임계 경로는 **T0 → T1 → T3 → T4**다. T2·T5·T6·T9는 T1 이후 병렬 가능하다.

권장 착수 순서: T0+T1을 한 bump로 묶고, 이어서 T2와 T3, 그다음 T4. T4가 끝나기 전에는
T11(밸런스)을 확정하지 않는다 — 행동 주기와 세그먼트 구조가 전투 길이를 결정하기 때문이다.

## 10. 구현 플랜 분할 지침

각 트랙을 구현 플랜으로 열 때 지킨다.

- 한 plan 파일 = 한 coding agent가 한 번에 수행할 수 있는 한 slice.
- 파일명 `fable_<주제>_step1_<YYMMDDHHMM>.md`, 보고서 `fable_<주제>_step2_report.md`.
- 필수 구성: baseline 커밋 → scope → §3의 하드 불변식 상속 → 검증 명령 → WP 목록(순서 고정, WP당 커밋 1개) → 명시적 범위 밖 → 최종 체크리스트.
- **다음 단계의 schema를 미리 확정하지 않는다.** 앞 slice의 public contract와 테스트를 보고 다음 plan을 만든다.
- 밸런스 값이 정해지지 않았으면 data-driven placeholder로 남기고 임의 숫자를 넣지 않는다.
- 시각 폴리시는 플랜 범위에서 제외하고 별도 step으로 진행하되, 신규 마크업의 클래스/데이터 속성은 플랜에서 계약으로 고정한다.
- subagent의 PASS/FAIL 보고를 믿지 않는다. cargo / pytest / npm 검증은 main이 WSL에서 재실행한다.
