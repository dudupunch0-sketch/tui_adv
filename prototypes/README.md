# 절차적 그래픽 연구 — 에셋 없이 게임 그래픽을 코드로 만들 수 있는가

이 디렉터리는 **결정을 위한 연구 기록**이다. 게임에 배선되지 않으며 배포되지도 않는다.

문제의식은 단순했다. 삽화 에셋을 구하는 일이 어렵고 비싸다. 그런데
[Vyom-26/Wave-Racer](https://github.com/Vyom-26/Wave-Racer) (프로젝트명 **INK TIDE**)는 메시·텍스처·사운드를
전부 런타임 생성으로 해결했다. 그 방법론을 우리 게임에 적용할 수 있는가?

결론부터: **적용할 수 있는 영역과 없는 영역의 경계선을 실측으로 찾았다.**
자세·모션·실루엣·천·이펙트는 코드가 잘 해낸다. **얼굴은 아니다.**

---

## 1. INK TIDE가 실제로 한 것

에셋 파일이 **0개**다(`.png`/`.glb`/`.mp3` 하나도 없음). 런타임 의존성은 `three` 하나뿐.

| 보통 에셋으로 푸는 것 | INK TIDE의 코드 대체물 |
|---|---|
| 바다 텍스처/노멀맵 | `water/gerstner.ts` — Gerstner 파 6개 합성, 버텍스 셰이더 변위 |
| 3D 모델 | `boat/boatMesh.ts`(53KB), `rider/riderRig.ts`(65KB) — `BufferGeometry` 직접 조립 |
| 환경맵(HDRI), 셰이딩 램프 | `render/textures.ts` — canvas 2D로 matcap을 **그림**, 램프는 `DataTexture` |
| 폼/스파클 스프라이트 | 원 90개를 겹쳐 찍고 `destination-out`으로 46개를 파냄 |
| UI 폰트/아이콘 | `ui/inkDraw.ts` — `Path2D` 도형 + 손으로 만든 7세그먼트 숫자 |
| 효과음 | `audio/audio.ts` — 오실레이터·노이즈·필터. `decodeAudioData` 없음 |

**베낄 값어치가 있는 건 기법이 아니라 네 가지 규율이었다.**

1. **`ARCHITECTURE.md`가 구속력 있는 계약** — "Zero external assets", "No PBR", "One palette",
   "One wave field", 파일 소유권 배타. 특히 "One wave field"는 CPU가 `sampleOcean()`,
   GPU가 `GERSTNER_GLSL`을 같은 uniform으로 먹는다. 갈라지면 배가 물 위에 뜨거나 잠기므로
   **물리적으로 강제되는 단일 진실**이다.
2. **팔레트 단일화** — `core/palette.ts`에 색이 전부 모여 있고, 주석이 *왜 그 색인지*를
   캡처 근거로 기록한다. `waterShadow`는 "그림자 전체에 waterDeep를 쓰면 비네트가 얹히는 순간
   *이미지에 뚫린 구멍*으로 읽힌다"는 실패에서 나왔다.
3. **결정론적 시드** — mulberry32 하나를 `?seed=`로 초기화. 구름 배치·AI 실수 타이밍·스파클이
   전부 이 스트림에서 나온다.
4. **스크린샷 하네스** — *"모든 시각적 주장은 캡처된 프레임으로 검증한다. 코드가 어떻게
   동작해야 하는지에 대한 추론으로는 절대 검증하지 않는다."*

`KNOWN_GAPS.md`로 "폼은 70% — 웨이크 리본이 스크롤/확산은 하지만 나이에 따라 소산하지 않음" 식의
정직한 미달 보고까지 갖췄다.

### 캐릭터를 만든 방식 (우리에게 가장 중요한 부분)

- **`riderRig.ts` (65KB) — 형태.** 뼈 22개. 지오메트리는 프로파일 스윕(`limbProfile`,
  `creasedLimb`, `knuckleProfile`)으로 생성. 스키닝을 직접 구현(정점당 뼈 행렬 2개).
  12개 파츠를 2개 지오메트리로 병합하고 파츠 색은 정점 속성 `aTint` → **라이더 1명 = 드로우콜 4개**.
- **`riderAnim.ts` (32KB) — 움직임.** *"클립도, 키프레임도, 외부 데이터도 없다. 매 프레임 포즈를
  상태에서 유도한다."* 네 층으로 쌓인다:

```
SIGNALS  →  STATES  →  MODIFIERS  →  IK
```

1. **SIGNALS** — 원시 상태를 애니메이터가 키를 잡을 값으로 변환(요 레이트, 종방향 G, 스로틀, 슬립)
2. **STATES** — 전신 포즈 5개. 각자 *절대 포즈*를 쓰고 가중 혼합 후 재정규화 → 전환이 자동
   크로스페이드고 포즈를 추가해도 기존 것을 안 건드림
3. **MODIFIERS** — 가산 레이어(균형 카운터롤, 턴 기울기, 체중 이동, 스카프 휘날림)
4. **IK** — 손을 핸들바에 풀어서 붙임. 주석: *"이 레이어가 설득력을 만든다"*

## 2. 핵심 발견 — 4층 구조는 차원과 무관하다

이 프로토타입의 중심 주장이다. `character-rig/rig.js`는 **렌더러를 모른다.**
2D 렌더러는 관절 각도를 캔버스에 실루엣으로 그리고, 3D 렌더러는 **같은 숫자**를
Three.js 계층의 `rotation.z`에 넣는다. 어느 쪽도 포즈를 계산하지 않는다.

그리고 우리 전투 큐 5종이 그 층에 그대로 대응한다:

| cue | 레이어 |
|---|---|
| `attack` | STATE (발도·베기, phase 매개변수) |
| `evade` | STATE |
| `incapacitated` | STATE (다른 상태를 덮어씀) |
| `hit` | **MODIFIER** — 가산 |
| `balance_broken` | MODIFIER + STATE |

`hit`이 상태가 아니라 수정자인 이유가 데이터에서 나왔다: 실제 픽스처에서 두 전투원이
**같은 tick에** 서로 때린다. 상태로 만들면 맞는 순간 공격이 사라진다.

**따라서 2D↔3D 전환은 되돌릴 수 없는 결정이 아니다.** 애니메이션 자산은 양쪽에 그대로 남는다.

## 3. 데이터는 전부 실제 코어 출력

지어낸 좌표를 쓰지 않았다. `crates/escape-core/examples/dump_combat_spectator.rs`가
게이트된 systemic 전투(`wuxia_combat_spectator_preview_bout`)를 해석해 `ScenePage.combat`을 덤프한다.

```bash
cargo run -p escape-core --example dump_combat_spectator -- 2 > combat-frames.json
```

8프레임 · `tick_millis=100` · flat-top axial `(1,0)→(4,0)` · `attack`/`hit`이 거의 매 tick ·
마지막 tick에 `incapacitated` · `outcome=mutual_defeat` · `core_log` 32줄 / `full_log` 64줄.

시드 고정 + 애니메이션 클럭 없음이므로 같은 명령이 항상 같은 바이트를 낸다.
렌더러를 고칠 때 before/after 비교가 의미를 갖는 조건이다.

| 라운드 | 산출물 | 결과 |
|---|---|---|
| 0. 기본 프로토타입 | `character-rig/` | 두 스타일 나란히, 전투 프레임 3개 |
| 1. 플레이 화면 경연 | `contest-style1/`, `contest-style2/` | 격리된 두 에이전트가 각자 모바일 세로 플레이 화면 제작 |
| 2. 얼굴 라운드 | 같은 디렉터리 | 표정을 리그 층에 추가, 인물 설정 반영 |

경연은 **서로의 결과물을 못 보는 별도 worktree**에서 진행했다. 공유한 것은 `rig.js`뿐이다.

### 인물 설정

- **청류문 연서린** — 이십대 초반, 여성, 산발, 날카로운 이목구비, 냉정, 흉터 없음, 미형
- **흑사방 갈여청** — 여성 자객, 얼굴 노출, 미형, 청류문과 정반대 헤어(높게 묶은 머리)

체형이 비슷해졌으므로 진영 구분을 **색이 아닌 형태**로 재설계해야 했다(접근성 계약).
풀어헤친 산발 vs 묶은 머리 / 직검 vs 곡도 / 긴 밑단 vs 짧은 밑단+정강이 감발 /
등에 걸린 삿갓 vs 없음. 양쪽 모두 색을 뺀 실루엣으로 검증했다.

## 5. 캡처가 잡아낸 것 — 이 연구의 가장 값진 산출물

**전부 코드를 읽어서는 찾을 수 없었고, 실제 프레임을 눈으로 봐야 나온 것들이다.**
INK TIDE의 규율이 왜 필요한지에 대한 직접 증거다.

### 공통 / 기본 프로토타입
- `taperedPath`가 `ctx.arc()`로 끝을 둥글리려다 **관절마다 완전한 원**을 남겼다
  (arc는 캡이 아니라 서브패스를 추가한다)
- 검로 호가 2.1rad을 쓸어 프레임을 가로질렀다 — 그 캐릭터의 베기가 아니라 배경 장식으로 읽혔다
- 3D 도포 원뿔(46 단위)이 다리를 전부 삼켜 **종 모양**이 됐다
- 3D 전완이 피부색이라 소매가 맨팔로 읽혔다

### 스타일 1 (2D 본 리그) — 약 14 캡처 라운드
- 컷 트레일이 *들어올린* 칼에서 회색 쐐기를 늘어뜨리고 칼끝 너머로 흰 파편을 남김
- 소매·감발 끝단 캡이 로브 뒤에서 각진 블록으로 삐져나옴
- 상체가 앞으로 숙여질 때 허리끈 끝이 **위로** 흔들림
- `poseDown`(엉덩이를 바닥에)이 읽을 수 없는 더미로 캡처됨 → 무릎 꿇는 자세로 수정
- 칼끝 충돌 판정이 한 번도 안 걸림 — 칼은 **중간**에서 교차한다
- `fillSkin`이 적의 정수리를 통째로 덮어칠해 **대머리 자객**이 됨
- 풀어헤친 머리 덩어리가 로브 뒤에 100% 가려짐
- 등에 건 삿갓이 엉덩이에 걸려 견갑으로 읽힘

### 스타일 2 (3D 셀 셰이딩) — 약 15 캡처 라운드
- 커스텀 `ShaderMaterial`은 **출력 색공간 변환을 받지 못한다** — 화면 전체가 반 스톱 어두웠다.
  추측을 멈추고 `calibrate.html`/`probe.mjs`로 **실측**(0x808080 → 128이 아니라 55)
- 팔레트 연산이 선형 공간에서 돌아 **모든 검정에 가까운 색이 황갈색**이 됨
- 옷깃·허리끈·부츠코·모자끈이 `+Z` 기준으로 만들어졌는데 리그 정면은 `+X`
- attack phase 0.56에서 45단위 칼날 두 자루가 상대를 **관통**
- `bladeGeo`가 쿼드를 역방향으로 감아 노멀이 안쪽을 향함 → 앞면 컬링, **BackSide 잉크 헐만 렌더**.
  검 두 자루가 3라운드 동안 새까맸는데 의도한 것처럼 보였다
- 칼날의 넓은 면이 상대를, 날이 카메라를 향해 45단위 검이 **머리카락 한 올**로 투영됨
- 시선 오프셋이 눈별 미러에 곱해져 **모든 초상이 사시**
- `mouthCurve` 위에 입꼬리 올림 항이 겹쳐 **모든 표정이 비웃음**
- 머리 덩어리를 `az≈0`(= `+X`, 그녀가 *바라보는* 방향)에 배치해 코 위로 커튼이 내려옴
- 머리 셸 앞면이 두개골 안으로 들어가 이마에서 z-파이팅 체커보드
- 구면 캡 하나로는 눈썹 위 테두리와 목덜미를 동시에 가질 수 없다 — 두 조각이어야 했다

**마지막 두 항목은 4배 확대에서만 보였다. 412px 실제 크기에서는 안 보였다.**
반대로 `poseDown` 문제는 실제 크기에서만 드러났다. **두 배율 모두 봐야 한다.**

## 6. 결론 — 절차적 생성의 경계선

### 6-1. 폰 세로 화면에서 보드 위 얼굴은 읽히지 않는다

두 에이전트가 **서로를 보지 못한 채 같은 결론**에 도달했다.

> 스타일 1: "보드 위 두상은 18px. 얼굴은 정보가 아니라 노이즈를 더한다.
> 표정 연기는 HUD 초상이 전부 한다."
>
> 스타일 2: "412px에서 보드 얼굴은 20px. 얼굴이 *있다*는 것과 머리 방향만 읽힌다.
> **컷인에 의존하고 있고, 그 사실을 밝힌다.**"

독립적 수렴이므로 취향이 아니라 구조적 사실이다.

### 6-2. 미형 얼굴은 코드로 만들기에 최악의 대상이다

두 결과 모두 레퍼런스 수준에 크게 못 미쳤다. 그리고 격차는 **칠하는 기술이 아니라 비례**에 있었다:
두개골이 넓고 턱이 무겁고 눈이 낮게 넓게 앉았다.

이유는 구조적이다. 사람의 지각은 얼굴 비례에 **몇 퍼센트 오차까지** 반응한다.
그런데 절차적 생성의 작업 방식은 *상수를 수정 → 캡처 → 육안 판단 → 다시 수정*이다.
화가가 직접 밀고 당기며 즉각 피드백 받는 것과 비교해 **대역폭이 압도적으로 낮다.**

INK TIDE가 코드로 성공한 대상을 보면 확인된다 — 파도, 선체, 거품, 라이더의 **자세와 움직임**.
전부 사람이 "정답 비례"를 외우고 있지 않은 대상이다. **그리고 라이더의 얼굴은
헬멧과 바이저로 가려져 있다.** 우연이 아니다.

### 6-3. 그래서 어디에 절차적 생성을 쓸 것인가

| 영역 | 방식 | 근거 |
|---|---|---|
| 보드 캐릭터·자세·모션 | **절차적** | 수량이 무한히 늘어남. 잡졸 20명이 서로 다르게 생기는 게 공짜 |
| 전투 이펙트·천·검로 | **절차적** | 시뮬레이션 상태에서 유도됨 |
| 장면 삽화 | **절차적 또는 생성형** | 44개 이상이고 계속 증가 |
| **인물 초상** | **직접 제작 (소수 정예)** | 등장인물 수로 상한이 걸림. 품질이 결정적. 절차적 생성이 가장 못하는 영역 |

원래의 고통(*"에셋 구하기가 어렵고 비싸다"*)은 **수량에 비례**한다. 초상은 수량이 유한하다.
명명된 캐릭터 5~10명 × 표정 4개 = 20~40장이고 한 번 만들면 끝이다.

## 7. 두 스타일 비교 (플레이 화면 기준)

| | 스타일 1 (2D 본 리그) | 스타일 2 (3D 셀 셰이딩) |
|---|---|---|
| 폰 크기 가독성 | **강함** — 평면 색면이 축소에 강함 | 보통 — 디테일이 412px에서 녹음 |
| 천의 관성 | **verlet 헴이 실제로 끌림** | 원뿔이 기울 뿐 |
| facing / 카메라 각도 | 좌우 반전만 | **실제 회전, 각도 자유** |
| 런타임 의존성 | 0 | Three.js |
| 드로우콜 | 캔버스 1개 | **전투원당 ~60** (예산은 라이더당 4) |
| 얼굴 그림 품질 | 둥글고 무거움 | **텍스처 자체는 더 잘 그려짐** (`face.js`) |
| 배포까지 남은 일 | 적음 | **병합 + 정점 스키닝 필요 (미계상)** |

스타일 2의 `face.js`는 **렌더러 비의존 Canvas 2D 페인터**다. 구면 UV로 작업할 뿐,
그리는 로직(눈 구조, 눈꼬리 각도 `EYE.tilt`, 홍조, 입술 하이라이트)은 평면에도 그대로 옮겨진다.
스타일 2의 자체 기록: *"눈꼬리는 바깥으로 들어올린다 — 인형 같은 얼굴과 날카로운 얼굴을
가르는 게 대부분 이것이다."*

## 8. 남은 격차 (정직하게)

**양쪽 공통**
- `evade` / `balance_broken` 포즈와 표정은 작성됐지만 **이 픽스처가 그 큐를 만들지 않아 미검증**
- 전투원 2명이 한 줄에 인접한 **단 하나의 배치**만 확인했다. 다른 헥스 배치에서 인물이
  겹치는지 아무도 검증하지 않았다
- 로그가 매 tick 거의 동일하다. 데이터에 충실한 결과지만 다양한 `template_id`에서는 미검증

**스타일 1**
- 원거리 눈이 초상 크기에서 거의 동공뿐이다
- 삐져나온 가닥이 이마 위 긁힌 자국으로 읽힌다
- 보드 하단에 죽은 공간이 남고 비네트로 가릴 뿐 구도가 해결하지 못했다
- `poseDown` 무릎꿇기는 IK 없이 각도로 손 배치했다 — `HIP_HEIGHT`가 바뀌면 깨진다

**스타일 2**
- **드로우콜 미병합** — 보드 타일은 4쌍으로 병합됐지만 인물은 파츠마다 메시+헐
- 머리 회전은 **치트**다(코드에 그렇게 명시). 두 인물이 교전선을 따라 서고 카메라가 정면이라,
  ±35° 목/머리 스윙과 반대 회전 홍채가 없으면 얼굴이 아예 안 보인다
- 잔머리 가닥이 412px에서 가는 철사로 읽힌다 — *"여기가 2D 렌더러가 나를 이길 지점이고
  나는 못 닫았다"*
- 도포는 강체 원뿔이다
- `debug.mjs`, `calibrate.html`, `probe.mjs`는 배포되지 않을 진단 도구다

```bash
cd prototypes/contest-style1   # 또는 contest-style2
npm install
PLAYWRIGHT_CHROMIUM_PATH=/path/to/chrome node capture-playscreen.mjs
```

`PLAYWRIGHT_CHROMIUM_PATH`는 브라우저가 이미 설치된 머신에서 버전별 다운로드를 건너뛰기 위한
것이며, 생략하면 Playwright 기본 해석을 따른다.
