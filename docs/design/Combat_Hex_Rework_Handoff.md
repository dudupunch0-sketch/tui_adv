## 1. 한 장 요약

**무엇을 하고 있나.** 사용자가 제공한 육각 타일 오토배틀러 레퍼런스(스크린샷 5장 + 전투 1라운드
영상 2편)를 기준으로 `escape-core`의 전투 시스템을 구체화하는 중이다.

**어디까지 왔나.** 좌표계 트랙(T1)과 행동 주기 트랙(T3)이 끝났다. 전투는 이제 육각 타일 위에서
점유를 지키며 유닛별 리듬으로 움직인다. 테스트 **354 → 434**.

**다음은 무엇인가.** **T4(실행 모델·개입·지속)**. 리워크에서 가장 넓고 되돌리기 비싼 트랙이며,
세그먼트 실행·save schema·프레임 데이터 규모가 한꺼번에 걸린다. 한 슬라이스로 가면 안 된다.

**가장 중요한 규율 하나.** 플랜에 **정지 조건**을 적고, 구현자가 기대값을 조용히 고치지 못하게
막고, 오케스트레이터가 보고서를 믿지 말고 **직접 재검증**한다. 이 루프가 이번 세션에서 실제 결함
세 개를 잡았다(§6).

## 2. 배경 — 왜 이 리워크인가

레퍼런스 분석과 현재 코드 대조 결과, 방향이 어긋난 게 아니라 **해상도가 낮았다**. `escape-core`는
이미 결정론적 seed, 동시 tick, 좌표 위 자동 전투, 판정과 분리된 관전 view라는 같은 뼈대를 갖고 있었다.

부족한 것은 세 층이었다.

| 층 | 리워크 전 | 현재 |
|---|---|---|
| **공간** | 타일·점유 없음. 말들이 서로를 통과함 | **해결됨** (T1) |
| **시간** | tick은 있으나 행동 주기 없음. 매 틱 전원 이동 + 매 틱 전체 공격 | **해결됨** (T3) |
| **표현** | cue 5종뿐. 수치·스택·스킬명을 그릴 데이터가 없음 | **남음** (T5 + T8) |

레퍼런스 실측 상세는 [Combat_Hex_Rework_Development_Plan.md](Combat_Hex_Rework_Development_Plan.md) §1에 있다.

## 3. 확정된 결정 — 임의로 바꾸지 않는다

사용자가 승인한 결정이다. 뒤집으려면 사용자에게 물어야 한다.
전체 21항목은 [개발 플랜 §2](Combat_Hex_Rework_Development_Plan.md#2-확정된-방향)에 있고, 여기엔
**이어받는 사람이 특히 오해하기 쉬운 것**만 옮긴다.

1. **파견/웨이브/보스/복귀 루프는 차용하지 않는다.** 전투 1회 = 인카운터 1개라는 현행 위상 유지.
   레퍼런스의 상점·드래프트·전투 중 레벨업·시너지 태그는 전부 범위 밖이다.
2. **개입은 유지한다.** 0~3회, 개입 플래그 발생 시 정지, 선택이 전투에 영향을 준다.
   레퍼런스는 순수 관전형이지만 **우리는 아니다.** 이게 이 프로젝트를 레퍼런스와 가르는 축이다.
3. **픽셀아트로 가지 않되 나중에 교체하기 쉽게 시스템화한다.** 차용 대상은 그림체가 아니라
   **정보 문법**(칸 분할 체력 바, 플로팅 수치, 스택 표기, 말풍선, 점유 하이라이트, 대시 잔광).
4. **전투불능(체력 0)은 회복으로 되돌릴 수 없다.** 대신 **부활**이 별개 기능으로 존재하고
   체력 100%로 되돌린다. 이 둘의 대상 조건은 상호 배타적이다.
5. **대형 유닛은 대칭 형태만 쓴다** (2026-08-07). 회전이 없어서 비대칭 형태는 아군·적이 같은
   방향을 향하고, 고치려면 미러가 필요한데 그건 회전을 이름만 바꿔 들여오는 것이다.
   **연결성은 코드로 막고 대칭성은 콘텐츠 규칙으로 둔다** — 나중에 회전이 필요해질 때 열 수 있게.
6. **T1 이후 순서는 T3 → T4** (2026-08-07). 임계 경로를 따른다. 대가로 화면은 당분간
   로그·보고서 위주로 남는다.
7. **공격속도는 숫자로 노출하지 않는다.** 내부 계산이며 로그·관전 표면 어디에도 값이 나가면 안 된다.

## 4. 지금까지 지어진 것

### T0 — `simulation_version` 강제 검증 (#195)

정본 03의 "결정성은 같은 version 내부에서만 보장한다"를 코드로 강제한다.
`CURRENT_SIMULATION_VERSION` 하나만 지원하며, **index-time**(`validate_encounter_combat` 규칙 12)과
**runtime**(`CombatSimulation::new`) 두 곳에서 거부한다.

**역직렬화는 일부러 막지 않았다.** 옛 version이 박힌 저장 기록은 계속 읽혀야 한다 —
막으면 기존 저장이 깨진다. 금지되는 것은 그 version으로 **새로 시뮬레이션을 돌리는 것**이다.

> 이 슬라이스가 실제로 잡은 것: 트리에 `v1`(Rust 픽스처 7개 파일)과 `v2`(저작 콘텐츠)가
> **공존하고 있었다.** 아무도 몰랐고 검사를 붙이는 순간 65개 테스트가 떨어져 드러났다.

### T1 — 육각 좌표계 (#195, #196, #197)

| 슬라이스 | 내용 |
|---|---|
| T1-a | `combat_hex.rs` — axial `HexCoord`, 거리·인접·`ring`/`range`/`line`, `HexShape`, `HexOccupancy`. **순수 모듈, 배선 없음** |
| T1-b1 | `CombatPosition`/`CombatFacing` 삭제 → `HexCoord`. 이동이 타일 단위, 사거리가 육각 거리. `v2` → `v3` bump |
| T1-b2 | web 정합. **축좌표 → 화면좌표 변환을 정규화 앞에** 넣음 |
| T1-c | 점유 강제(생성·경로·목적지 3지점) + 포위 판정 파생 함수 |
| T1-d | 대형 유닛 발자국(`occupies`), 거리를 **발자국 최솟값**으로 |

**`combat_hex.rs`는 동결이다.** T1-a가 확정했고 이후 슬라이스가 소비만 한다. 부족하면 우회하지 말고
그 사실을 보고한 뒤 별도로 연다.

**세 규약이 계약이 됐다** — 이웃 방향 순서 상수, `line()` tie-break, `HexShape` 정규형.
각각 모듈 주석에 적혀 있고 이름 붙은 테스트가 고정한다.

> 이 트랙이 실제로 잡은 것: **말들이 서로를 통과해 tick 3부터 좌우가 뒤바뀌던 결함.**
> 정본 09의 "화면 왼쪽 아군 / 오른쪽 적"을 재생 중에 위반하고 있었다.

### T3 — 행동 주기 (#197)

**누적 게이지 모델.** 매 tick `gauge += speed`, `gauge >= 10_000`이면 행동하고 차감한다.
정수 hundredths만 쓴다.

- 정수 간격("N틱마다")을 쓰지 않은 이유: 1.5배속을 표현할 수 없고 속도 버프에 반올림 규칙이 필요해진다.
- **드레인은 루프다.** 속도 2배면 한 틱에 두 번 행동한다. `if`로 쓰면 조용히 틱당 1회로 잘려
  속도 버프가 그 위로 무의미해진다.
- **이동 주기와 공격 주기는 분리**한다. 공격 주기는 `CombatAttackDefinition`에 붙는다 —
  한 전투원이 리듬이 다른 여러 공격을 가질 수 있다.
- 반복 이동은 같은 직선의 한 번의 긴 걸음으로 **접고**, 반복 공격은 **N개의 독립 결과**로 낸다.
  후자는 굴림이 같으면 빠른 공격이 항상 두 번 맞거나 항상 두 번 빗나가기 때문이다.
  굴림은 기존 `roll()` 파생에 `fire_index`를 섞으며 **새 난수원이 아니고**,
  `fire_index == 0`이 이전 값을 그대로 재현해 기본 경로가 바이트 단위로 같다.

## 5. 남은 트랙

전체 정의는 [개발 플랜 §6](Combat_Hex_Rework_Development_Plan.md)에 있다. 여기엔 상태와 순서만 적는다.

### T4 — 실행 모델 · 개입 · 지속 ← **다음**

**리워크에서 가장 중요하고 가장 넓다. 반드시 3~4 슬라이스로 쪼갠다.**

네 가지가 한 트랙에 묶여 있는 이유는 서로를 필요로 하기 때문이다.

**(a) 세그먼트 실행.** 지금은 전투를 통째로 계산한 뒤 재생한다(`resolve` → `conclude` → `spectate`).
개입이 결과를 바꾸려면 이렇게 되어야 한다.

```
core가 tick 0..k 실행 → opportunity 감지로 "k에서 정지"를 결정론적으로 판정
  → 세그먼트[0..k] 프레임 + 개입 마커를 렌더러에 전달
  → 렌더러는 k까지 재생하고 정지 → 플레이어 선택
  → 선택을 입력으로 세그먼트[k+1..] 실행
```

**개입 지점은 core가 정하고 렌더러는 거기까지 재생 후 멈춘다.** 렌더러가 임의 시점에 멈추면
개입 시점이 wall-clock에 의존해 결정론이 깨지고, 렌더러가 정지 시점을 판단하면 정본 13을 깬다.

**tick 내부 순서를 계약으로 고정해야 한다: 판정 적용 → 개입 기회 감지 → 결착 판정.**
개입형 부활("마지막 한 명이 쓰러지는 순간")이 이 순서에서만 성립한다.

**(b) 세그먼트별 seed 파생.** 지금은 전투 1회 = seed 1개다. 선택 이후 구간의 난수가 선택에
의존하되 같은 선택 이력이면 같은 결과여야 한다.

**(c) 전투 진행 상태 저장.** 매 렌더 재실행 모델을 폐기한다. 아래 규모 문제와 같은 답이다.

**(d) 이동·판정 패스 인터리빙.** T3가 남긴 것 — 지금도 **전투불능 전투원이 결착 전 tick에서
계속 이동한다.** `execute_combat`(이동)이 `resolve`(피해)보다 먼저 통째로 돌기 때문이다.

**규모 제약 (설계 전제).** 현재 저작 전투는 `tick_millis: 100`, `max_ticks: 10` — 1초 8틱이다.
2분이면 **1,200틱**, 150배.

| 항목 | 현재(8틱, 2명) | 2분(1200틱, 12명) |
|---|---|---|
| `frames[].pieces` | 16 | **14,400** |
| `full_log` | 32 | **26,000+** |
| `ScenePage.combat` JSON | 수 KB | **수 MB** |

지금은 결정론이라 재실행 결과가 같아 문제가 안 드러났을 뿐이다. 대응은 세그먼트 저장 + 델타 인코딩
+ 논리 tick 굵기 재조정이며, 세 번째는 "화면 시간 = 시뮬레이션 시간"(I1)을 건드리므로 별도 결정이다.

**여기서 `CombatPresentationSpeed`를 재생 레이어로 옮긴다** (T0에서 이관됨).

## 6. 작업 방식 — 이게 실제로 효과가 있었다

이 세션의 루프는 **플랜(오케스트레이터) → 구현(subagent) → 오케스트레이터 직접 검증**이었다.
아래 규칙들이 실제 결함을 잡았으므로 그대로 이어받기를 권한다.

### 6-1. 플랜에 정지 조건을 적는다

구현자가 우회하지 말고 **멈추고 보고할** 조건을 명시한다. 이번에 쓴 것:

- 기존 테스트가 하나라도 값이 바뀌면
- fingerprint가 바뀌면
- 플랜 서술이 실제 코드와 다르면 (**코드가 이긴다. 단 그 사실을 보고한다**)
- 플랜이 두 가지로 읽히면
- 동결 파일에 부족한 게 있으면

### 6-2. "기대값을 조용히 고치지 마라"

**가장 값이 컸던 규칙이다.** 판정에 영향을 주는 변경에서는 예외 없이 적었다.

> 기대값을 새 결과에 맞춰 고쳐야 통과하는 상황이 오면 멈추고 보고한다.
> 그건 플랜의 분석이 틀렸다는 뜻이고, 슬라이스를 오늘 착지시키는 것보다 그 사실을 아는 게 중요하다.

단, **투영식이 바뀌는 것 같은 표시 변경에서는 규칙이 반대**다. 그때는 "움직인 이유를 설명할 수 있을 때만
고치고, 설명 못 하면 멈춘다"로 바꿔 적었다. 둘을 구분하지 않으면 규칙이 무의미해진다.

### 6-3. 보고서를 믿지 않는다

AGENTS.md의 검증 신뢰 원칙 그대로다. 영향이 큰 검증은 오케스트레이터가 직접 재실행한다.
이번 세션에서 매 슬라이스마다 `cargo test --workspace`, `npm test`, `cargo fmt`,
`git diff --check`, 소유 범위 밖 변경 여부, 금지 파일 무변경을 직접 확인했다.

**보고서가 놓친 것을 실제로 잡았다** — 예: 한 슬라이스가 "4개 파일"이라 보고한 픽스처 문제가
실제로는 7개 파일 9곳이었다.

### 6-4. 두 갈래로 검증한다

"기존 값이 안 바뀌었다"만 확인하면 **아무것도 강제하지 않은 변경이 초록으로 통과한다.**
그래서 점유 강제 슬라이스에서는 두 가지를 함께 요구했다.

1. 고정 테스트 값이 그대로인가
2. **좌표가 실제로 달라졌는가** (관통이 사라졌는가)

### 6-5. 실측 후 넘긴다

플랜을 쓰기 전에 오케스트레이터가 직접 숫자를 재고, 그 예측을 플랜에 명시했다.

> 예: "두 전투원이 모두 `r = 0`에 있어 육각 거리가 `|dq|`로 줄어들고 기존 유클리드 거리와
> 정확히 같으므로, 좌표 교체가 이 전투의 거동을 바꾸지 않아야 한다."

예측이 맞았고, 틀렸다면 구현자가 즉시 알아챘을 것이다. **구현자에게 발견하게 맡기지 않는다.**

## 7. 이 저장소에서 밟기 쉬운 함정

### 7-1. 소유 파일 목록 — 컴파일 때문에 바뀌는 파일

**이번 세션에서 세 번 연속 틀렸다.** 원인은 매번 같다: "의미적으로 바뀔 파일"만 세고
**"컴파일되려면 바뀌어야 하는 파일"**을 빠뜨린다.

구조체에 필드를 추가하면 그 구조체를 명시적 리터럴로 만드는 **모든** 파일이 깨진다.
`Default`가 없으면 스타일 문제가 아니라 하드 컴파일 에러다.

**대책**: 필드 추가·타입 변경 슬라이스에는 코드를 건드리기 전에 생성 지점을 세는 WP를 맨 앞에 둔다.

```bash
grep -rln "CombatSimulationParticipant {" crates/
grep -rln "CombatAttackDefinition {" crates/
```

T3에서 이걸 넣었더니 **착수 5분 만에** 목록이 나왔고 중간에 멈추는 일이 없었다.

### 7-2. cargo/npm은 이 컨테이너에 있다

AGENTS.md는 "cargo·wasm-pack·gh는 WSL에만 있다"고 적는데 그건 **사용자 머신** 기준이다.
클라우드 컨테이너에는 cargo 1.94.1과 npm이 있다. 구현자에게 이걸 명시하지 않으면
"환경 탓에 검증 불가"라는 보고가 나온다 — AGENTS.md에 정확히 그 환각 보고 사례가 기록돼 있다.

없는 것: **`wasm-pack`**. 그래서 `npm run qa:storybook:visual`은 앱이 상호작용 상태에
도달하지 못해 5뷰포트가 전부 실패한다. **회귀 때문이 아니다.**
전투 화면이 게이트 뒤에 있어 어차피 시각 QA로는 아무 차이도 안 보이므로,
그 게이트는 게이트 해제 슬라이스의 몫이다.

### 7-3. 번들은 재생성한다

`crates/escape-core/fixtures/content/storypack-preview/*.bundle.json`과
`web/src/data/generated/storypack-preview/*.bundle.json`은 export 산출물이다.
**손편집하지 말고** `scripts/export_web_data.py`로 재생성한다.

주의: 생성 번들 하나가 `web/` 아래 있어서 "web 무변경" 같은 소유 규칙과 문구가 충돌하기 쉽다.
경로를 명시해서 쓴다.

### 7-4. version bump가 필요한 때와 아닐 때

- **필요**: 직렬화 표현이 바뀔 때 (`{x,y}` → `{q,r}`)
- **불필요**: `#[serde(default, skip_serializing_if = ...)]`로 **미설정 시 키가 아예 안 나타날** 때.
  T1-d(`occupies`)와 T3(속도 필드) 둘 다 이 방식으로 bump 없이 착지했다.

bump가 필요해 보이면 먼저 "기본값이 현재 동작이고 키가 사라지게 할 수 있나"를 확인한다.

### 7-5. 게이트 플래그

저작된 전투 인카운터 `wuxia_combat_spectator_preview_bout`은
`combat_spectator_preview_unlocked` 플래그 뒤에 있고 **일반 플레이 경로에서 도달 불가**다.
그 플래그를 세우는 콘텐츠는 없다. 해제는 렌더러가 갖춰진 뒤 별도 슬라이스의 몫이다.

### 7-6. 패닉 정책

이 크레이트는 어디서도 패닉하지 않는다. 잘못된 입력은 `Result`로 거부하고 산술은 checked다.

`.expect()`는 **구조적으로 도달 불가능한 경우에만** 허용한다.
"실제로 일어날 수 있는 실패를 삼키는" 코드와 구분해야 한다 —
전자의 예는 `footprint_tiles`가 빈 벡터를 반환할 수 없는 경우이고,
후자의 예는 점유 실패를 `let _ =`로 버려서 그 타일이 빈 칸으로 읽히게 만든 코드였다(수정됨).

## 10. 이어받는 사람에게

권하는 시작 순서.

1. 이 문서와 [개발 플랜](Combat_Hex_Rework_Development_Plan.md)을 읽는다. 다른 건 아직 읽지 않는다.
2. `cargo test --workspace --no-fail-fast`로 **434 / 0**을 직접 확인한다. 다르면 그것부터 해결한다.
3. `crates/escape-core/src/combat_hex.rs`의 모듈 주석을 읽는다 — 세 규약이 거기 있다.
4. T4를 3~4 슬라이스로 쪼개는 플랜을 쓴다. §5의 (a)~(d)와 규모 제약이 입력이다.
5. 슬라이스마다 §6의 규율을 적용한다. 특히 **정지 조건**과 **직접 재검증**.

**가장 조심할 것**: T4는 save schema 결정을 품고 있어 되돌리기가 비싸다.
한 슬라이스로 밀어붙이지 말고, 앞 슬라이스가 확정한 public contract를 보고 다음 플랜을 쓴다
(운영 정본 §5의 분할 규칙).

**전투가 "읽히게" 만드는 일(T5 + T8)은 T4 뒤다.** 그동안 화면이 로그 위주로 남는 것은
사용자가 대가를 알고 선택한 순서다. 순서를 바꾸려면 사용자에게 확인한다.
