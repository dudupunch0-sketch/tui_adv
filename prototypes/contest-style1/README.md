# 전투 캐릭터 리그 — 스타일 프로토타입

전투 관전 표면에 세울 **캐릭터를 에셋 없이 코드로 만드는** 두 가지 방식을,
같은 실제 전투 데이터로 렌더해 비교하기 위한 프로토타입이다. 결정용이며 배포되지 않는다.

배경: [Vyom-26/Wave-Racer](https://github.com/Vyom-26/Wave-Racer) (INK TIDE)가 메시·텍스처·사운드를
전부 런타임 생성으로 해결했고, 그 중 캐릭터에 해당하는 부분이 `rider/riderRig.ts`(형태)와
`rider/riderAnim.ts`(움직임)다. 여기서 차용한 것은 3D가 아니라 **애니메이션 구조**다.

## 핵심 주장

`rig.js`는 렌더러를 모른다. INK TIDE `riderAnim.ts`의 4층 구조 —

```
SIGNALS → STATES → MODIFIERS → IK
```

— 는 차원과 무관하며, 두 렌더러가 **같은 관절 각도**를 소비한다. `rig2d.js`는 캔버스에
실루엣으로 그리고, `rig3d.js`는 같은 숫자를 Three.js 계층의 `rotation.z`에 넣는다.
어느 렌더러도 포즈를 계산하지 않는다.

큐 5종이 포즈 레이어에 그대로 대응한다:

| cue | 레이어 |
|---|---|
| `attack` | STATE (발도·베기, phase로 매개변수화) |
| `evade` | STATE (뒷발 중심 회피) |
| `incapacitated` | STATE (붕괴, 다른 상태를 덮어씀) |
| `hit` | **MODIFIER** — 가산. 공격 중에도 피격될 수 있어야 한다 |
| `balance_broken` | MODIFIER + STATE 혼합 |

`hit`이 상태가 아니라 수정자인 이유: 실제 픽스처에서 두 전투원이 **같은 tick에**
서로 때린다. 상태로 만들면 맞는 순간 공격이 사라진다.

| 파일 | 역할 |

## 전투 화면 목업 (스타일 1)

`playscreen.html`은 인물만 비교하던 시트를 넘어서, 실제로 출시될 법한 표면을
그린다. 화면의 **모든 수치가 픽스처에서 나온다**:

- 점유 칸 `(2,0)`/`(3,0)`과 이동 흔적은 프레임 그대로. 주변 빈 칸만 문맥으로 추가한다.
- 기력 바 = `damage_applied` 항목의 누적. t4에서 정확히 53/107, t8에서 0/107.
- 로그 6줄은 등록된 `template_id` 4종을 한국어 문장으로 옮긴 것. 없는 사건은 만들지 않는다.
- tick 안에서 **누가 먼저 움직이는지**는 `core_log`의 sequence 순서에서 읽는다
  (아군 1–2, 도전자 3–5). 그래서 한쪽은 베는 중, 다른 쪽은 아직 들어올리는 중이다.
  좌우 대칭 두 인물은 그림이 아니라 도표로 읽혔다.

축 좌표 → 화면 변환은 `renderCombatStage.ts`와 같은 flat-top 공식이고,
그 뒤에 붙는 세로 압축(0.6)은 좌표계가 아니라 **카메라**다.

```bash
cd prototypes/character-rig && npm install
PLAYWRIGHT_CHROMIUM_PATH=/path/to/chrome node capture-playscreen.mjs
```

두 번 돌리면 바이트가 같다 (시드 고정 + 애니메이션 클럭 없음).

## 재현

데이터는 지어낸 좌표가 아니라 코어가 실제로 만든 프레임이다.

```bash
cargo run -p escape-core --example dump_combat_spectator -- 2 \
  > prototypes/character-rig/combat-frames.json

cd prototypes/character-rig && npm install
PLAYWRIGHT_CHROMIUM_PATH=/path/to/chrome node capture.mjs
```

시드 고정 + 애니메이션 클럭 없음이므로 같은 명령은 항상 같은 바이트를 낸다.
`PLAYWRIGHT_CHROMIUM_PATH`는 브라우저가 이미 설치된 머신에서 버전별 다운로드를 건너뛰기 위한 것이며,
생략하면 Playwright 기본 해석을 따른다.

## 캡처가 잡아낸 것 (반영 완료)

추론이 아니라 실제 프레임이 잡아낸 결함들이다. 전투 화면 목업까지 8라운드.

- `taperedPath`가 `ctx.arc()`로 끝을 둥글리려다 **관절마다 완전한 원**을 남겼다 (arc는 캡이 아니라 서브패스를 추가한다)
- 검로 호가 어깨+칼날 반지름으로 2.1rad을 쓸어 프레임을 가로질렀다 — 그 캐릭터의 베기가 아니라 배경 장식으로 읽혔다
- 리그 자신의 이전 phase 칼끝을 이어 리본으로 바꾼 뒤에도, **들어올리는 중**의 검로는
  프레임 밖을 향하는 회색 쐐기가 됐다. 검로는 베는 구간에만 나온다.
- 현재 칼끝까지 리본에 넣으면 가장 굵은 곳이 칼끝에 걸쳐 **칼 앞으로 삐져나온 흰 조각**이 됐다
- 피격 스파크 9개가 몸통을 덮어 캐릭터에 붙인 파편처럼 보였다. 초승달 1개로 줄여도
  같은 이유로 실패했다 — 이 크기에서 몸통 위의 밝은 표식은 **아이콘**이다. 지금은 없다.
- `poseDown`이 엉덩이를 바닥에 붙이자 **읽을 수 없는 천 더미**가 됐다. 실루엣 어휘가
  전부 수직인 리그는 척추가 눕는 순간 남는 게 없다. 무릎 꿇림으로 다시 썼다.
- 무릎을 꿇려도 치마가 퍼지지 않으면 "서 있는데 작아진" 것으로 읽혔다
- 소매·팔목 감개를 **먼 쪽 팔에도** 그려서, 평평한 끝단이 로브 뒤에서 삐져나온 사각 조각이 됐다
- 허리끈 자락을 골반 프레임에서 그려 상체가 숙이면 **위로 솟았다**. 천은 중력을 따른다.
- 도(刀)가 0.42rad + 중배 부풀림이라 **낫**으로 읽혔고, 코등이·고리는 상대 가슴 위의 장신구였다
- 적 진영 문양은 마름모 clip이 inset ring을 잘라 **글자 주변 화살촉 4개**를 남겼다
- 3D 도포 원뿔(46 단위)이 다리를 전부 삼켜 **종(鐘) 모양**이 됐다
- 3D 전완이 피부색이라 소매가 맨팔로 읽혔다
- 셀 밴드 사다리가 어두운 로브를 전부 그림자 대역에 넣었다

## 선(線) 무게 결정

이 렌더러는 **잉크 실루엣**이라 채워진 도형마다 단단한 키라인이 붙는다.
필요한 얼굴은 그 반대 — 선 없이 값과 부드러운 경계로 형태를 잡는 그림이다.
둘은 그냥 섞이지 않는다. 택한 해법은 만화의 해법, **중요도에 따라 선 무게를 바꾸는 것**:

- 옷·강철·신발은 키라인을 온전히 유지한다. 18px에서 인물을 붙잡아 주는 것이 그것이다.
- **피부에는 키라인이 없다.** 머리의 윤곽은 머리카락·깃·판 배경과의 *값 차이*가 지고,
  안쪽은 전부 부드러운 그라디언트다.
- 눈은 예외이자 증거다 — 속눈썹은 단단하지만 그것은 **윤곽선이 아니라 이목구비**다.

기각한 두 안: 전부 부드럽게 가면 화면 크기에서 몸의 실루엣이 무너지고,
얼굴까지 완전 셀로 가면 일관되지만 두 인물에게 지정된 섬세함을 버리게 된다.

## 남은 격차 (정직하게)

전투 화면 목업 기준.

- **아군 소매가 아직 덩어리다.** 넓은 장삼 소매 + 커프스 밴드로 팔로는 읽히지만, t8의
  늘어뜨린 팔에서는 무릎 위에 접어놓은 천처럼도 읽힌다.
- **얼굴이 여전히 밝은 타원이다.** 앞머리·귀밑머리를 넣어 민머리 느낌은 없앴지만,
  정책상 이목구비가 없는 이상 원거리에서 "머리"라는 정보 이상은 주지 못한다.
  적은 삿갓 그림자로 이 문제를 구조적으로 피해 가는데, 아군에는 같은 장치가 없다.
- **합(合) 섬광이 이 픽스처에서 한 번도 뜨지 않는다.** 두 칼날 선분이 실제로 교차할 때만
  그리도록 했고, t1–t8 어디서도 교차하지 않는다. 코드 경로가 캡처로 검증되지 않았다.
- **보드 아래쪽 1/4이 비어 있다.** 들어올린 칼에 여유를 주려고 카메라를 올려 잡았고,
  아무도 칼을 들지 않은 tick에서는 그만큼 아래가 남는다. tick마다 카메라를 바꾸면
  화면이 흔들려서 하지 않았다.
- **동작 흔적 표식(점/×)이 이 픽스처에서는 칸 하나씩만 나온다.** 이동이 t1→t2 한 번뿐이라
  표식 체계가 실제로 붐비는 상황에서 검증되지 않았다.
- `evade` / `balance_broken` 포즈는 **작성됐지만 캡처되지 않았다.** 이 픽스처는 두 큐를 만들지 않는다.
- **로그에 전투불능 줄이 없다.** `core_log`에 해당 template이 없어서, 결착은 배너와
  카드의 취소선 태그만 말한다. 없는 줄을 지어내지 않은 결과다.
- 3D 쪽 격차는 그대로다 (병합/스키닝 없음, 도포가 천이 아님).

## 배치 프로브 — 렌더러가 이 픽스처 하나에만 맞는지 (측정)

`combat-frames.json`은 **한 줄(r=0)에서 인접하는 2인**만 만든다. 그 배치 하나로
튜닝된 보드가 다른 배치에서도 성립하는지 확인하려고, `CombatSpectatorView`와 같은
모양의 **합성** 페이로드를 만들어 손대지 않은 렌더러에 통과시켰다
(`arrangements.html` + `capture-arrangements.mjs`). 시트의 합성 칸은 전부
`PROBE 합성`으로, 실측 칸 2개는 `실측`으로 표시된다. 게임 로직이 아니라
**렌더러 속성**(배치·겹침·가독성·그리기 순서)을 재는 것이라 합성 입력이 정당하고,
합성임을 화면에 표시하는 것이 그 조건이다.

측정 (보드 실크기 362×409px, 얼굴 없는 변형):

| 배치 | hex s | 인물 높이 | 판정 |
|---|---|---|---|
| 1 한 줄 2인 (실측 · 자동 카메라) | 29px | 72px | 성립하지만 작다 |
| 2 원거리 q0↔q7 | 20px | 49px | **실패** — 인물이 뭉개진다 |
| 3 대각 인접 | 38px | 95px | 성립 |
| 4 수직 인접 (같은 q) | 45px | 113px | **실패** — 뒤 인물 ~65% 가려짐 |
| 5 3인 일렬 | 33px | 82px | 성립 (겹침 있음) |
| 6 포위 1대3 | 38px | 95px | **경계** — 주인공이 가장 안 보인다 |
| 7 혼전 6인 | 29px | 72px | **경계** — 같은 편끼리 구분 불가 |
| 8 한 줄 2인 (출고 상수 카메라) | 64px | 160px | 성립 |

찾은 결함 (이번 커밋에서 고치지 않았다):

- **카메라가 상수다.** 출고 화면은 `zoom 1.30 · focus (q2.5, r−0.46)`을 하드코딩한다.
  이 픽스처에서만 맞다. 프로브는 전부 자동 카메라(점유 칸 무게중심 + contain)로 그렸고,
  자동 카메라는 아무것도 보드 밖으로 내보내지 않지만 여백이 남아 인물이 절반 크기가 된다.
  실제로는 점유 칸 bbox fit + hex 크기 하한이 필요하다.
- **수직 인접이 최악이다.** 같은 q에서 r이 1 다르면 화면 세로 간격이
  `√3·s·squash ≈ 0.52·s`(s=45px에서 23px)뿐인데 인물은 113px다. 앞 인물이 뒤 인물을
  거의 다 덮는다. 그리기 순서 자체는 **옳다** (화면 y 오름차순 = 먼 것부터).
- **포위에서 구도가 뒤집힌다.** 장면의 주인공(포위당한 쪽)이 앞 열 적에 가려져
  가장 안 보이는 인물이 된다. 깊이 정렬은 맞고 연출이 틀렸다.
- **같은 편 개체를 구분할 수 없다.** 보드에 말별 이름표·cue 칩이 없고(그래서 충돌할 것도 없다)
  HUD는 카드 2장 고정이다. 3인 이상의 정체성은 미해결이다.
- **`signalsFor`가 상대를 `find(p => p.id !== piece.id)`로 고른다.** 3인 이상에서 가장 가까운
  적이 아니라 배열의 첫 타인을 잡으므로 `dist`/`closing`이 틀린다. 2인 픽스처에서는
  드러나지 않던 버그다.
- **검로 리본이 다시 떨어져 나온다.** 칼끝이 빠른 위상에서 회색 삼각 파편이 칼 옆에 남는다
  (프로브 3·4·6·7에서 모두 보인다).
- 어느 배치에서도 **보드 밖으로 나가는 인물은 없었다.** 진영 구분(밝은 celadon + 산발 +
  직검 + 긴 헴 ↔ 어두운 자주 + 묶은 머리 + 곡도 + 등의 삿갓 + 너덜한 헴)은
  **6인에서도, 얼굴 없이도** 유지됐다.
